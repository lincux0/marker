# 开源与发布指南

源码公开、push、远端 CI、上传安装包与修改仓库可见性是独立操作。本文列维护者检查流程，不声称全部完成；当前证据见[建设历程](progress.md)。公开前应把仓库视为可能已被完整复制，之后删除文件或改回私有都不能撤回已复制内容。

## 源码公开前

- 核对 MIT `LICENSE`、第三方声明及源码/图标/字体/样例来源；项目 MIT 不改变组件许可。
- 检查当前树和完整 Git 历史中的令牌、私钥、数据库、草稿、个人内容、内部路径和提交邮箱。删除当前文件不能消除历史对象。
- 历史检查结果与覆盖范围以[建设历程](progress.md)本轮记录为准；模式扫描不等于不存在敏感信息。现有提交含个人邮箱，旧测试含本机绝对路径。公开前由维护者决定邮箱是否可公开；历史清理需另定备份与协作者迁移方案，不能直接强推。
- 确认默认分支、权限、分支保护及公开的安全政策。GitHub 当前仅允许公开仓库启用私密漏洞报告；公开后立即按下节操作启用并验证入口。
- 检查 README、贡献指南、安全政策和用户指南中的支持范围、构建步骤、已知限制及联系方式；早期版本没有长期支持分支或固定安全响应时限，不要暗示正式签名或全面兼容。
- 检查 GitHub Actions 的权限与 secrets：默认分支工作流只需要最小权限，不把个人凭据或签名密钥设为公开构建必需条件；查看公开后实际运行记录。
- 从干净克隆检查文档、锁文件及构建；不要求私有 SDK、作者证书或本机绝对路径，旧手动脚本按工程指南调整夹具。
- 图片及样例不含真实用户内容；缓存、私钥和用户数据不纳入 Git。

## GitHub 公开仓库操作

以下设置由仓库维护者在 GitHub 上执行。先确认仓库所有者、默认分支、协作者权限和可公开范围，再按[GitHub 仓库可见性说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility)检查公开的影响；公开后仓库内容可被任何人访问和复制。

公开前确认默认分支已包含 [SECURITY.md](../SECURITY.md)，且说明备用联系办法。将仓库设为 Public 后，立即进入 **Settings → Security & quality → Advanced Security** 启用 **Private vulnerability reporting**，再用仓库 **Security → Advisories → Report a vulnerability** 实际检查表单；若入口不可用，不要宣称已启用，先修复设置或明确私密联系渠道。参照 [GitHub 私密漏洞报告配置说明](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/configure-for-a-repository) 与[报告漏洞说明](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/report-privately)。

核对 Issues、Pull requests、Actions、Wiki、Discussions、Pages 和下载区的启用状态及内容；检查 Issue/PR 模板、Dependabot 更新策略，关闭不准备维护的入口。检查 Actions 工作流权限、缓存和日志不会暴露凭据或用户数据。保留默认分支保护/规则、最小写权限及 MFA 等账户保护。GitHub 的[仓库规则集说明](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository)可用于维护分支与标签规则。

完成源码与历史审查、公开分支推送和远端 CI 核对后，在 Settings 中改为 Public。公开后立即启用并验证私密漏洞报告入口，再用未登录浏览器或无写权限账户复查仓库主页、默认分支、LICENSE、README、SECURITY、Issue/PR 模板及入口；检查 Actions 实际运行及 artifact（当前发布流程应提供未签名 MSIX、Setup 与对应 SHA-256）、仓库可见性和下载链接。记录实际结果；CI 正在运行或配置存在都不等于远端工作流已成功。仓库变为 Public 不等于新 Release 已发布；二进制发布仍按下文单独执行。

## 版本构建与验证

1. 选择发布提交、保持工作区干净并记录 commit。版本以 `Package.appxmanifest` 和工程配置为准，对齐后再建标签。
2. 在支持的 Windows x64 运行 `./scripts/bootstrap.ps1`、`./scripts/build.ps1`，记录通过/跳过/失败；不用 `-UpdateLockfile` 绕过锁定还原。
3. 运行 `./scripts/build-setup.ps1` 与 `./scripts/build.ps1 -Package`。仅同一源码、资源、输出已验证时可用 Setup `-SkipBuild`。
4. 核对 EXE、Web 与包内容。Setup/MSIX 应含 `LICENSE.txt`、`THIRD_PARTY_NOTICES.md` 及 `licenses` 下 MIT、Apache-2.0、WebThirdParty、NuGetThirdParty、Markdig 文本。依赖变更后重新生成 Web 聚合并检查 diff；微软运行时与 NuGet 传递组件条款仍需逐项复核。
5. 执行相关现有回归。包内容不等于安装，网页 mock 不等于原生实测；打开/保存/恢复/冲突、中文路径/输入法、键盘/辅助功能安排实机验收。
6. 隔离核对安装、启动、升级、卸载、打开方式与数据保留。`test-setup-associations.ps1` 拒绝接管已有安装，不绕过保护。
7. 使用受信任凭据签名，核验发布者及签名，再安装验收。开发证书只用于隔离测试，结束清理临时信任，不要求公众导入测试证书。

最低 build、多屏/混合 DPI、长期使用、正式签名与生产 MSIX 安装仍有待验范围；每版明确预览状态和已知问题，不因本机构建成功宣称全面支持。

## 上传发行版

- CI artifact 应含未签名 MSIX、Setup 及与对应 Setup 匹配的 SHA-256，不自动建 Release；另行检查选定提交的实际远端运行结果和产物内容。
- 上传对应提交的安装包，提供版本、要求、依赖、变更、已知问题和 SHA-256；签名改变内容，校验值须在最终签名后生成。
- Setup 脚本生成 `.sha256`；其他资产用 `Get-FileHash -LiteralPath '<产物路径>' -Algorithm SHA256`，不复制旧版本哈希。
- 下载链接指向实际发布资产；复核下载后的内容、签名与哈希。工作区 `artifacts/` 不是公开下载地址。
- 标签、Release、资产上传和可见性变化分别需维护者授权；普通源码 push 不包含这些操作。

## 推送核对

先 `git fetch origin`，核对 ahead/behind、全部待推提交与 diff。精确暂存本次文件；正常推送，非 fast-forward 时核对协作者新增内容，不强推覆盖。

推送后比较 HEAD 与 `git ls-remote origin refs/heads/master`（其他分支按实际替换），确认哈希一致和工作区状态；CI 另验。只记录实际结果，不把 push 写成公开仓库或发行版已发布。
